## 🎪 What this repo is

Welcome to **BACKStack** 🤘 — Backstage + ArgoCD + Crossplane + Kyverno, four tools that really did not need to spell out a cool acronym but did anyway. This is the KubeCon NA 2025 workshop/demo repo: a GitOps-based platform engineering stack running on a local `kind` Kubernetes cluster, built to show off what happens when you let a developer merge a PR and a robot army handles the rest.

Most of the repo is Kubernetes YAML and Backstage configuration, not application code — there is no monolithic build/test pipeline for the repo as a whole. The one real codebase is the Backstage instance under `backstage/source`. Everything else is manifests, policies, and glue that makes the GitOps magic trick work.

## 🛠️ Environment setup / commands

The intended workflow is either GitHub Codespaces (`.devcontainer/`) or manual local setup per `MANUAL_SETUP.md`. `.devcontainer/post-create.sh` is the canonical, up-to-date sequence for bootstrapping the whole stack (cert-manager, ingress-nginx, Kyverno, Crossplane, ArgoCD, RBAC, metrics-server, ArgoCD ingress) — prefer reading/updating that script over `MANUAL_SETUP.md` when the two diverge, since it's what Codespaces actually runs. Think of `MANUAL_SETUP.md` as the director's commentary and `post-create.sh` as the movie itself.

Bootstrap order matters and later steps depend on earlier ones being healthy (e.g. Crossplane's `provider-kubernetes` must reach `Healthy=true` before provider configs/XRDs/compositions are applied — skip ahead and you'll just be yelling at a cluster that isn't ready to listen). Key sequence:
```bash
kind create cluster --name backstack-demo --config kind/config.yaml
# cert-manager, ingress-nginx, kyverno, crossplane, argocd installs...
kubectl apply -f crossplane/01-functions
kubectl apply -f crossplane/02-providers
kubectl wait --for condition=Healthy=true providers.p crossplane-contrib-provider-kubernetes --timeout 10m
kubectl apply -f crossplane/03-provider-configs
kubectl apply -f crossplane/04-xrds --recursive
kubectl apply -f crossplane/05-compositions --recursive
kubectl apply -f crossplane/06-examples --recursive
kubectl apply -f kyverno/
```

### Backstage (`backstage/source`, Yarn v4 workspace)
```bash
cd backstage/source
yarn install
yarn start                 # runs both frontend (app) and backend workspaces
yarn build:all              # backstage-cli repo build --all
yarn build:backend          # yarn workspace backend build
yarn test                   # backstage-cli repo test
yarn test:all                # with coverage
yarn test:e2e                 # playwright test (packages/app/e2e-tests)
yarn lint                    # lint changed files since origin/master
yarn lint:all                 # lint everything
yarn fix                      # backstage-cli repo fix (autofix)
yarn prettier:check
```
To run a single package's tests/lint: `yarn workspace app test`, `yarn workspace backend lint`, etc. (each workspace under `packages/*` and `plugins/*` has its own `test`/`lint` script via `backstage-cli package ...`).

Required env vars before starting Backstage: `GITHUB_TOKEN`, `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `GITHUB_OWNER`, `GITHUB_REPO`, plus cluster-derived `KUBERNETES_URL`, `KUBERNETES_SERVICE_ACCOUNT_TOKEN`, and `ARGOCD_ADMIN_PASSWORD` (see `MANUAL_SETUP.md`). `NODE_OPTIONS="--max_old_space_size=8192 --no-node-snapshot"` and `NODE_TLS_REJECT_UNAUTHORIZED=0` are required for local runs — yes, Node really does want 8GB of headroom just to say hello.

### ArgoCD access (no ingress/LB in kind by default for local runs)
```bash
kubectl port-forward -n argocd svc/argocd-server 8080:443 &
export ARGOCD_ADMIN_PASSWORD=$(kubectl get secret -n argocd argocd-initial-admin-secret -o jsonpath='{.data.password}' | base64 --decode)
argocd login --username admin --password $ARGOCD_ADMIN_PASSWORD localhost:8080 --insecure
```

## 🏗️ Architecture

### GitOps flow (the core mechanism tying everything together, aka "the trick")
This is the whole show. Six steps, zero manual `kubectl apply`s once it's wired up:

1. A developer creates/updates an application by adding or editing a YAML manifest under `demo-cluster/<namespace>/<Kind>/<name>.yaml` (in this repo's case, typically via a PR — either hand-written or generated by a Backstage software template / the GitOps Manifest Updater plugin).
2. ArgoCD's `ApplicationSet` (rendered from `argo/app-set-template.yaml` via `envsubst`, using `GITHUB_OWNER`/`GITHUB_REPO`) uses a **git file generator** matching `demo-cluster/*/*/*.yaml`. Path segments encode `demo-cluster/<namespace>/<kind>/<file>.yaml`, and the Application name/namespace/source path are derived directly from those segments (templated with Go templates, e.g. `{{ index .path.segments 1 }}`).
3. ArgoCD auto-syncs (prune + selfHeal + CreateNamespace) the manifest into the cluster — no human required, no human wanted.
4. Crossplane's Composite Resource Definitions (XRDs) and Compositions turn the high-level manifest (e.g. `App`, `WebApp`, `ClusterApp`) into real Kubernetes resources (Deployment, Service, Ingress, HPA) via `provider-kubernetes`.
5. Backstage's Kubernetes Ingestor plugin polls the cluster (10s interval, configured in `backstage/values-templated.yaml`) and auto-creates/updates catalog entities for discovered Crossplane composites, and auto-generates Backstage Software Templates from XRDs.
6. Kyverno policies (audit mode by default) validate the composite resources against org rules and surface violations in Backstage via the Kyverno plugin — the friendly hall monitor, not the bouncer.

So: **adding a new YAML file under `demo-cluster/` is the deployment mechanism** — merge a PR, walk away, come back to running infrastructure. That's the demo.

### Crossplane layout (`crossplane/`)
Numbered directories represent apply order, and this convention is important when adding a new service offering — the numbers aren't just for show, they're load-bearing:
- `01-functions/` — Crossplane composition Functions (go-templating, KCL, patch-transform, pythonic) used as pipeline steps in Compositions.
- `02-providers/` — Crossplane Providers (currently `provider-kubernetes`, which lets Crossplane manage arbitrary K8s resources) plus provider RBAC/DeploymentRuntimeConfig.
- `03-provider-configs/` — auth/connection config for providers.
- `04-xrds/` — CompositeResourceDefinitions: the platform APIs exposed to developers (`App`/`ClusterApp` = basic-app, namespaced vs cluster-scoped; `WebApp` = web-app, adds autoscaling/FQDN/ingress).
- `05-compositions/` — the implementation of each XRD (which Function pipeline turns the XRD spec into managed resources); mirrors the `04-xrds` subdirectory names.
- `06-examples/` — sample Composite Resource instances developers would create.

When adding a brand-new service offering (as walked through in `docs/end-to-end/lab-guide.md`), the pattern is: create matching subdirectories under `04-xrds/<name>` and `05-compositions/<name>`, define the XRD schema (only expose the fields you want developers to control — resist the urge to expose everything, future you will thank present you), implement a Composition pipeline (often `function-go-templating`), then `kubectl apply` both — and grant Crossplane RBAC for any non-`provider-kubernetes` CRDs it needs to manage (e.g. CNPG's `postgresql.cnpg.io` cluster resources).

### Kyverno policies (`kyverno/`)
All policies target the Crossplane XRD kinds (`App`, `ClusterApp`, `WebApp`) directly, in `validationFailureAction: Audit` mode (report-only, not enforced — these policies judge silently, they don't block):
- `require-autoscaling-webapps.yaml` — WebApps must have `spec.scaling.enabled: true`.
- `unique-ingress-host.yaml` — WebApp FQDNs must be unique across existing Ingresses (uses a Kyverno `apiCall` context to query live Ingress state).
- `nginx-not-allowed-policy.yaml` — disallows the `nginx` image across App/ClusterApp/WebApp (demo policy for image restrictions — nginx did nothing wrong, it's just a good example).
- `policy-rbac.yaml` — grants Kyverno's background/reports controllers read access needed for background scanning.

### Backstage (`backstage/source`)
Standard Backstage monorepo (Yarn v4 workspaces): `packages/app` (frontend, role: frontend) and `packages/backend` (role: backend), plus `plugins/*` for any custom plugins. Notable third-party plugins wired in via `app-config.yaml` / package.json: TeraSky Crossplane resources & Kyverno policy reports plugins, Kubernetes Ingestor, GitOps Manifest Updater, Scaffolder Utils, MCP Actions backend, ArgoCD (redhat-argocd) plugin. `backstage/values-templated.yaml` is the Helm values file (templated with env vars like `GITHUB_OWNER`, `KUBERNETES_URL`, `ARGOCD_ADMIN_PASSWORD`) used to deploy Backstage via Helm in the containerized/Codespaces path; `app-config*.yaml` inside `backstage/source` are the app's own config layers (local vs production). Custom UI nav lives in `packages/app/src/modules/nav/Sidebar.tsx`. Catalog sources (`examples/entities.yaml`, `examples/org.yaml`, `examples/template/`) define the seed catalog; `examples/org.yaml` must have its GitHub username placeholder (`vrabbi`) updated per MANUAL_SETUP.md when doing a fresh manual setup.

### Documentation structure
`docs/01-getting-started.md` is the entry point, branching into `docs/end-to-end/lab-guide.md` (a full scripted walkthrough of both the developer and platform-engineer personas, including step-by-step screenshots referenced from `docs/images/`) and `docs/component-docs/` (per-tool deep dives). Treat `docs/end-to-end/lab-guide.md` as the authoritative source of intended user-facing workflows when making changes that affect the demo flow.

## 🎯 The vibe

This is a *demo* repo — it exists to make platform engineering look effortless on stage. When in doubt, favor changes that keep the story clean: a small PR should still trigger the full pipeline reliably, docs should stay honest about what's automated vs. manual, and nothing should require a human to babysit a `kubectl apply` that GitOps was supposed to handle for them. If a change makes the demo more fragile, that's a bug even if the YAML is technically correct.
